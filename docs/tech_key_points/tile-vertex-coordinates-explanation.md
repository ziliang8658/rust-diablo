# 等轴测瓦片顶点坐标详解

## 关键理解

**重要**：问题不在于几何重叠，而在于**精灵移动时的边界情况**和**渲染顺序**。

## 瓦片顶点坐标计算

### 前提假设

在Diablo的等轴测渲染中，`targetBufferPosition` 通常是**瓦片的底部中心点**（用于blocks 0-1），而不是顶部中心点。

### 墙壁瓦片 (2, 1) → screen(100, 50)

**假设 `targetBufferPosition = (100, 50)` 是底部中心点：**

```
四个顶点坐标：
1. 顶部中心点：(100, 50 - 32) = (100, 18)
2. 左侧顶点：  (100 - 32, 50 - 16) = (68, 34)
3. 底部中心点：(100, 50) ← 参考点
4. 右侧顶点：  (100 + 32, 50 - 16) = (132, 34)
```

**可视化：**
```
       (100, 18)  ← 顶部中心
          ●
         ╱│╲
        ╱ │ ╲
       ╱  │  ╲
(68,34)●  │  ●(132,34)  ← 左右顶点
       ╲  │  ╱
        ╲ │ ╱
         ╲│╱
          ●
       (100, 50)  ← 底部中心（参考点）
```

### 地板瓦片 (3, 0) → screen(164, 50)

**假设 `targetBufferPosition = (164, 50)` 是底部中心点：**

```
四个顶点坐标：
1. 顶部中心点：(164, 50 - 32) = (164, 18)
2. 左侧顶点：  (164 - 32, 50 - 16) = (132, 34)
3. 底部中心点：(164, 50) ← 参考点
4. 右侧顶点：  (164 + 32, 50 - 16) = (196, 34)
```

**可视化：**
```
       (164, 18)  ← 顶部中心
          ●
         ╱│╲
        ╱ │ ╲
       ╱  │  ╲
(132,34)●  │  ●(196,34)  ← 左右顶点
       ╲  │  ╱
        ╲ │ ╱
         ╲│╱
          ●
       (164, 50)  ← 底部中心（参考点）
```

## 关键发现

**共享顶点**：(132, 34) - 墙壁的右侧顶点 = 地板的左侧顶点

**但是**：这两个瓦片的菱形边界**并不重叠**！

```
墙壁右边缘：从 (132, 34) 到 (100, 50)
地板左边缘：从 (132, 34) 到 (164, 50)

这两个边缘在 (132, 34) 相交，但方向相反，不重叠！
```

## 那么问题在哪里？

### 问题1：精灵移动时的边界情况

从代码注释可以看出：

```cpp
// Render objects behind walls first to prevent sprites, that are moving
// between tiles, from poking through the walls as they exceed the tile bounds.
```

**关键理解**：
- 精灵在移动时，可能会**跨越瓦片边界**
- 精灵的渲染位置可能**不完全在它当前所在的瓦片内**
- 精灵的像素可能会**延伸到相邻瓦片的区域**

### 问题2：渲染顺序的重要性

即使两个瓦片在几何上不重叠，渲染顺序仍然重要：

```
错误的渲染顺序：
1. 渲染墙壁 (2,1) → 精灵在地板 (3,0) 上，但还没渲染地板
2. 渲染地板 (3,0) → 精灵被渲染，但此时墙壁已经渲染过了
   问题：精灵可能从墙壁边缘"穿透"显示

正确的渲染顺序（提前渲染）：
1. 提前渲染地板 (3,0) → 精灵被渲染在地板上
2. 渲染墙壁 (2,1) → 墙壁覆盖重叠区域（如果有）
   结果：精灵被正确遮挡
```

### 问题3：墙壁的blocks 2+向上延伸

从代码可以看到，墙壁有多个blocks向上堆叠：

```cpp
targetBufferPosition.y -= TILE_HEIGHT;  // 向上移动32像素
for (uint_fast8_t i = 2, n = MicroTileLen; i < n; i += 2) {
    // 渲染blocks 2, 3, 4, 5... 向上堆叠
    // 每个block向上偏移32像素
}
```

**这意味着**：
- 墙壁的blocks 2+会向上渲染
- 这些blocks可能会在Y方向上延伸到地板的区域
- 虽然blocks 0-1的边界不重叠，但blocks 2+可能会影响视觉

## 实际场景示例

### 场景：精灵从地板 (3,0) 向右移动到墙壁 (2,1) 附近

```
时刻1：精灵在地板 (3,0) 上
- 精灵位置：screen(180, 50)（在地板瓦片内）
- 精灵大小：假设 32×48 像素

时刻2：精灵向右移动，接近墙壁
- 精灵位置：screen(140, 50)（接近墙壁右边缘）
- 精灵的右半部分：screen(140-156, 50-74)
- 问题：精灵的右半部分可能延伸到墙壁的右边缘区域

时刻3：如果先渲染墙壁，再渲染地板
- 墙壁渲染：覆盖了 screen(68-132, 18-50) 区域
- 地板渲染：覆盖了 screen(132-196, 18-50) 区域
- 精灵渲染：在地板上，但精灵的右边缘可能在 screen(132-140) 区域
- 结果：精灵可能"穿透"墙壁显示

时刻4：如果先渲染地板（包括精灵），再渲染墙壁
- 地板+精灵渲染：先绘制
- 墙壁渲染：后绘制，覆盖重叠区域
- 结果：精灵被正确遮挡
```

## 总结

1. **几何边界**：两个瓦片的菱形边界在 (132, 34) 共享一个顶点，但边缘不重叠
2. **实际重叠**：问题不在于几何重叠，而在于：
   - 精灵移动时可能跨越边界
   - 精灵的像素可能延伸到相邻瓦片区域
   - 墙壁的blocks 2+向上延伸，可能影响视觉
3. **渲染顺序**：即使没有几何重叠，正确的渲染顺序（先地板后墙壁）仍然重要，确保精灵被正确遮挡

## 代码注释的关键信息

```cpp
// A proper fix for this would probably be to layout the scene and render by
// sprite screen position rather than tile position.
```

这说明：
- 当前的实现是基于瓦片位置的渲染
- 理想情况下应该基于精灵的屏幕位置渲染
- 但为了简单，采用了提前渲染的hack方案
