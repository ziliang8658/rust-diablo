# 文档写作风格指南：TinyRenderer 式教学文档

## 目的

本文描述 `rust-diablo` 项目中“实现完成后的教学文档”应采用的写作风格。参考对象是 TinyRenderer 课程文档的教学节奏：用一个很小、可运行、可观察的图形程序，把复杂渲染系统拆成连续的实验，每一节都让读者先看到问题，再通过代码和图像一步步修正。

这不是要求照搬 TinyRenderer 的主题或文本，而是学习它的教学组织方式：从现象出发、边写边验证、用输出结果解释算法。

## 总体风格

教学文档要像带读者一起写一段代码，而不是像 API 手册或论文综述。

- 先给一个可以运行的最小场景，让读者知道本节最终会看到什么。
- 每次只引入一个核心概念，例如一条线、一个三角形、一次坐标转换、一层遮挡关系。
- 不要一开始讲完所有理论。先让读者看到朴素实现，再指出它为什么不够。
- 每个改进都要能被观察到：日志、截图、像素差异、测试输出、帧序变化、地图索引变化等。
- 数学和术语要服务于正在解决的问题。先讲“为什么需要它”，再给公式或定义。
- 文档应保留“思考路径”：错误方案、边界情况、修正理由和验证方式都很重要。

## 推荐章节结构

实现完成后的教学文档建议使用下面的结构。可以按 step 内容调整，但不要丢掉“问题 -> 实验 -> 修正 -> 验证 -> 回到原版”的主线。

### 1. 本节要做什么

用白话说明这个 step 在游戏里解决什么问题。

示例：

- “我们要让玩家不再永远画在墙上面，而是像原版 Diablo 一样，被前景墙体遮住。”
- “我们要让 CL2 的 RLE 数据变成屏幕上能看到的战士动画帧。”

这一节要包含：

- 最终可观察结果。
- 本节只做什么。
- 本节明确不做什么。

### 2. 先做一个最小实验

从最小可运行代码或最小数据开始。不要直接展示最终版本。

可以是：

- 一个只画一条线/一个瓦片/一个角色的 example。
- 一个只解析一个资源文件头的测试。
- 一个只打印关键坐标转换结果的调试入口。
- 一个固定种子的地牢生成片段。

关键是让读者能立刻运行，并看到“现在还不完整”。

### 3. 观察问题

像调试课程一样描述当前实现哪里不对。

- 哪个像素、坐标、索引、帧、图层或状态不符合预期。
- 为什么肉眼看起来不对。
- 如果有截图或日志，要解释读者应该看哪里。

不要只写“存在 bug”。要把 bug 变成可观察现象。

### 4. 引入原版实现

这时再回到 DevilutionX C++ 源码。

必须写清：

- 参考文件路径。
- 关键函数。
- 关键数据结构或全局数组。
- 原版控制流的核心顺序。

解释重点不是“逐行翻译”，而是回答：

- 原版为什么需要这一步。
- 这一步解决了前面实验中的哪个问题。
- 它依赖哪些历史格式、坐标系统、渲染顺序或性能约束。

### 5. 映射到 Rust

把原版实现拆成 Rust 中的等价部件。

推荐用表格：

| 原版 C++ | Rust 实现 | 等价关系 | 差异原因 |
| --- | --- | --- | --- |
| `dPlayer[x][y]` | `World::d_player` | 瓦片到玩家索引的 O(1) 查找 | Rust 用 `Vec<Vec<i32>>` 管理边界 |

这一节要说明：

- 哪些地方是行为等价。
- 哪些地方只是当前 step 的简化。
- 哪些地方是 Rust 为了安全、所有权或错误处理做出的表达差异。

### 6. 一步一步改进

按 TinyRenderer 的节奏，把最终实现拆成几轮小改进。

每一轮建议包含：

- 这一轮修什么。
- 修改了哪些关键函数或结构。
- 为什么这样改。
- 改完以后如何观察效果。

不要一次贴巨大最终代码。只展示关键片段，并链接到真实文件。

### 7. 验证结果

验证要具体。

- 自动测试：写出命令和通过情况。
- 手动验证：写出运行入口、操作步骤、预期画面或日志。
- 对齐验证：说明和 C++ 原版比了什么。
- 未验证项：说明为什么没验证，缺资源、缺平台还是尚未实现。

如果涉及渲染，优先给截图、像素输出、帧序或图层顺序说明。

### 8. 常见误区

至少列出本 step 的真实坑点。

好的误区不是泛泛的“注意边界检查”，而是具体到项目：

- “`world` 坐标不能直接访问 `dPiece` 数组，必须加 `BORDER_SIZE`。”
- “移动中的玩家在原版里可能用负索引表达，当前 step 如果忽略它，要明确这是简化。”
- “CL2 和 CLX 都是 RLE，但帧表和透明段语义不能混用。”

### 9. 练习题

练习题应帮助读者继续探索，而不是只复述文档。

建议包含：

- 入门题：确认读者理解本节概念。
- 代码题：让读者改一个小功能并运行验证。
- 调试题：给一个现象，让读者定位可能的源码位置。
- 挑战题：讨论性能、边界、可视化工具或更接近原版的实现。
- 图形学/算法题：渲染、坐标、RLE、寻路、随机生成等主题要尽量结合实际游戏画面。

### 10. 回到大图景

最后说明本节在整个 Diablo 复刻中的位置。

- 它解锁了哪个后续系统。
- 哪些简化必须在后续 step 还债。
- 下一步最自然应该做什么。

## 语言规则

- 默认中文写作。
- 文件名、函数名、类型名、命令、资源名保持英文原文。
- 先白话，再术语；先现象，再理论；先最小例子，再完整系统。
- 可以用“我们”带读者推进，但不要写成聊天记录。
- 避免空泛形容词，例如“优雅”“强大”“高性能”。如果使用，必须说明证据。
- 代码片段要短，只放关键部分。完整代码用文件路径指向真实实现。

## 与前置文档的区别

教学文档写在实现完成之后，重点是“让读者学会这一步”。它不同于前置文档：

- 需求文档回答“要做什么、验收什么、不做什么”。
- 原版调研文档回答“C++ 原版怎么做、证据在哪里”。
- 设计文档回答“Rust 准备怎么映射、怎么拆结构”。
- 测试文档回答“怎么证明做对了”。
- 教学文档回答“这个系统为什么这样长出来，读者如何从零理解并复现这一小步”。

不要用教学文档替代前置文档；也不要把前置设计文档写成最终教程。前置文档要帮助实现不跑偏，教学文档要帮助学习和复盘。
